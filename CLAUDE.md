# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Nextrek ("Subspace Wumpus"): Hunt the Wumpus meets Asteroids, loosely based on 1971 BASIC *Star Trek*. A turn-based galaxy-exploration layer (the "hunt phase") drops into real-time top-down combat (the "kill phase") whenever the player moves into a sector holding hostiles. React 19 + TypeScript + Vite, bitECS for the combat simulation, Vitest for tests. Deployed to GitHub Pages on every push to `main` (`.github/workflows/deploy.yml`).

## Commands

```bash
npm run dev        # dev server with HMR
npm run build      # tsc -b && vite build - typecheck + production build to dist/
npm run preview    # serve the production build locally
npm run test       # vitest in watch mode
npm run test:run   # vitest run once - what CI runs
npm run lint       # oxlint
```

Running a single test file or test: `npx vitest run src/hunt/useGalaxy.test.ts` or `npx vitest run -t "some test name"`.

**Typecheck gotcha:** the root `tsconfig.json` uses project references with `files: []`, so a bare `npx tsc --noEmit` silently checks nothing. Use `npx tsc --noEmit -p tsconfig.app.json` (app code only) or `npx tsc -b --force` (what `npm run build` actually runs, both `tsconfig.app.json` and `tsconfig.node.json`).

## Architecture

### The hunt/kill boundary is a hard rule, not a convention

`src/hunt/` (turn-based exploration) and `src/kill/` (real-time bitECS combat) are kept **completely independent** - neither imports from the other. `src/game/GameShell.tsx` is the *only* file that imports from both; it's the phase-transition layer that decides when a hunt-phase move triggers or ends a kill-phase encounter, and folds the outcome (hull damage, leftover shield/phaser energy, kills) back into hunt state.

Because of this, small pieces of logic that both phases need are deliberately **duplicated** rather than shared (e.g. `degradedCooldownMultiplier` in `kill/KillPhase.tsx` is a local copy of `hunt/subsystems.ts`'s `degradedCostMultiplier`). Don't "fix" this by adding a cross-boundary import.

The one deliberate exception is `src/balance.ts`: every tunable gameplay constant (energy costs, mission length, seeding densities, combat damage, ship handling) lives there, and both `hunt/` and `kill/` import from it. This is safe because it's plain data with no behavior - domain modules import what they need from it and re-export under their original names, so it reads as if each module still defines its own constants.

### The galaxy is an undo-stack, not a mutable graph

`src/graph/UndoGraph.ts` is a graph whose node set and edge set are each a *stack* of snapshots. Every mutation pushes a new snapshot and, in lockstep, pushes the inverse operation onto a shared undo stack; `undo()` pops back to the previous configuration. This one mechanism drives two unrelated features:

- **Warp drive**: engaging it pushes a fast shortcut edge-set (`buildWarpEdges` in `hunt/warpNetwork.ts`, BFS-scoped to a radius); disengaging just calls `undo()`.
- **Subspace anomalies** (`graph/anomalies.ts`): a *barrier* strips every incoming edge to a sector (blocks entry, not exit); a *conduit* adds a bidirectional shortcut between two sectors. A *gate* (the third anomaly kind) isn't a graph mutation at all - it's a one-off random redirect computed in `hunt/anomalyEffects.ts`'s `pickGateDestination` and applied directly in `moveTo`.

The galaxy object itself lives **outside React state** (`useGalaxy.ts` holds it via `useMemo`, not `useState`) since mutating it doesn't need to trigger a re-render through the normal state-diffing path - `toggleWarp` just calls `bump()` (a version-counter `setState`) after mutating the graph directly.

### `useGalaxy.ts` is the hunt-phase state machine

The single largest file in the project. It owns `HuntState` (position, energy, subsystems, torpedoes, log, etc.) and every action that can change it: `moveTo`, `toggleWarp`, `allocateEnergy`, `adjustEnergy`, `resolveEncounter`, `longRangeScan`, `subspaceScan`. `status`/`defeatReason` (victory/timeout/stranded/destroyed) are derived each render from `hunt/mission.ts`'s pure functions, not stored directly.

**Watch out for stale closures here.** `resolveEncounter` is passed as a prop through `GameShell.tsx` into `KillPhase.tsx`'s world-building `useEffect`. If it closed over `state` directly, it would need `state.energy`/`state.subsystems` in its `useCallback` deps to stay fresh - giving it a new identity on every energy tweak, which propagates through `GameShell`'s `disengage`/`handleResolved` and causes `KillPhase` to tear down and rebuild its entire bitECS world (respawning hostiles at new random positions) on every unrelated state change. The fix in place: mirror `state` into a ref (`stateRef`) and read from that instead, so the callback's own identity stays stable. See `useGalaxy.test.ts`'s "keeps a stable function identity across unrelated state changes" test - this is a regression test for a real bug, not a hypothetical one.

**`allocateEnergy`'s `inCombat` parameter is a cost-model switch, not a display flag.** Shields/phasers energy is paid for up front (moved out of `reserve`) and only refunded lossily (`REFUND_EFFICIENCY`, 50%) when combat actually ends (`resolveEncounter`). Decreasing an allocation via `allocateEnergy` mid-fight used to be refunded at full 1:1 value instead, which let a player pump shields up, then drag the Engineering slider back down right before the fight resolved to dodge the 50% cost entirely. `inCombat` (true whenever `GameShell`'s `encounter` is non-null) makes a decrease pay the same lossy rate a real stand-down would. It defaults to `false` and there's only one call site today (`HuntPhase.tsx`'s `onAllocate`, passing `Boolean(encounter)`) - a second call site that forgets to pass it reopens the exploit silently, with nothing to catch the mistake at compile time. `adjustEnergy` (the H/P keyboard shortcuts' action) sidesteps this entirely by being increment-only - it never needs the flag.

### Galaxy generation and testability

The galaxy is a polar grid: rings around a galactic core, each ring with its own angular resolution (`hunt/cartography.ts`'s `sectorsInRing` - the innermost ring is coarser, the outer half finer), connected with Moore-neighborhood adjacency generalized across mismatched resolutions (`graph/polarTopology.ts`). Sectors are seeded probabilistically (hostile/anomaly/starbase densities, all in `src/balance.ts`) via an injectable `rng: () => number` parameter threaded through `createGalaxy`, `pickAnomalyPlacements`, `pickGateDestination`, `applySubsystemWear`, and `randomHomeSector` - this is what makes galaxy generation and combat outcomes deterministically testable. The one inconsistency: `moveTo`'s gate-redirect branch calls `Math.random` directly instead of taking an injectable rng, so tests that need a deterministic gate outcome mock `Math.random` globally instead.

The home sector is picked randomly each mission (`randomHomeSector`) but is always guaranteed clear of hostiles/anomalies/starbases - not by searching for an empty one, but because `createGalaxy`'s seeding loop unconditionally excludes whatever sector is designated home from every hazard roll.

### Barrier power-ups: a consolation prize, tracked outside the graph on purpose

Some barrier sectors (never gate or conduit - `BARRIER_POWERUP_CHANCE` in `balance.ts`, rolled only for `kind === 'barrier'`) also hold a resource cache, energy or torpedoes (`BARRIER_POWERUP_ENERGY_CHANCE` picks which), set on `AnomalyPlacement.powerUp` in `hunt/anomalySeeding.ts`. Entering the sector (`useGalaxy.ts`'s `moveTo`) fully refills that one resource and logs it, same as the barrier's own "collapses inward" message - no separate command, same as auto-docking at a starbase. It's deliberately never revealed by scanning: `GalaxyMap.tsx`'s power-up marker is gated on `visited`, not `anomalyKnown` (which long-range/subspace scans satisfy) - the whole point is that you don't know it's there until you've already paid the barrier's one-way cost to find out.

It's rechargeable, not one-shot: `HuntState.collectedPowerUps` (a `Map<NodeId, number>`) tracks the stardate a cache was last drawn, and `moveTo` grants it again once `BARRIER_POWERUP_COOLDOWN_STARDATES` have passed - the marker in `GalaxyMap.tsx` is likewise hidden while on cooldown, not just before the first visit. This turns out to reuse the entry-mode mechanic for free rather than needing anything new: `barrier()` only ever strips edges from whichever edge layer is "live" at entry time. An impulse entry strips the impulse edges directly - permanent, since that's the only layer there is, so the cooldown never gets a chance to matter. A warp entry only strips a layer stacked *above* the impulse edges, which is why it heals - meaning a warp-entered cache is the only kind worth the wait, and picking impulse trades that repeatability away for a single guaranteed draw. Collection is tracked in `HuntState` rather than by writing `powerUp: undefined` back onto the sector via `galaxy.setNode`. This is a deliberate dodge of a sharp edge in `UndoGraph`: `setNode` pushes onto the *same* shared `undoStack` that `toggleWarp`'s `disengageWarp()` pops from, and a barrier is exactly the kind of sector you can still be under warp when you first enter (see `warpEnteredBarrier` below) - a `setNode` call there would push an entry that a later `disengageWarp()` could pop instead of the warp edge-set, silently reverting the wrong thing while leaving warp still functionally engaged. (`GameShell.tsx`'s existing combat-result `setNode` call has this same latent risk today; it wasn't fixed as part of this, since it's pre-existing and orthogonal, but it's exactly the failure mode this feature was built to avoid repeating.) Keeping collection in React state instead sidesteps the whole class of bug rather than relying on call-order luck.

**A real bug the above surfaced, since fixed: disengaging warp after a warp-entered barrier heal used to not actually restore plain impulse edges.** `engageWarp`/`disengageWarp` (`hunt/galaxy.ts`) used to be a plain push/`undo()` pair, which only holds up if nothing else touches the graph while warp is engaged - entering a barrier under warp pushes its own edge-removal on top of the warp engagement itself (see `barrier()`'s note above), and a single `undo()` only popped that, leaving the full warp-radius network still live even though `state.warpEngaged` had gone false and the log said the barrier had healed. `engageWarp` now returns the graph's `undoDepth` from just before it pushed (a checkpoint), and `disengageWarp(galaxy, checkpoint)` unwinds everything back to that depth via `UndoGraph.undoTo` rather than assuming a single pop - correctly collapsing however many mutations happened mid-flight, not just the most recent one. `useGalaxy.ts`'s `toggleWarp` holds the checkpoint in a `useRef` (`warpCheckpointRef`), not `HuntState`, since nothing needs it to trigger a render. Confirmed the regression by reverting to a plain `galaxy.undo()` and watching the new `useGalaxy.test.ts` test ("restores real impulse neighbors after disengaging past a barrier entered mid-flight") fail exactly as expected - `galaxy.test.ts` has the same fix covered at the `engageWarp`/`disengageWarp` level directly. This shares the same known limitation as the `GameShell.tsx` combat-result `setNode` note above: `undoTo` unwinds *everything* pushed during a warp session indiscriminately, node mutations included, so a combat result landing on the shared stack mid-warp would also get reverted on disengage - not new (a single-pop disengage already risked reverting whichever mutation was topmost, arbitrarily), but worth knowing if that pre-existing risk ever gets addressed for real.

`StartScreen.tsx`'s `HINTS` pool (one shown at random per visit) has a line nodding at this - deliberately vague ("some hide something worth the risk of finding out"), naming neither the resource kind nor the odds, in keeping with the mechanic's own point that scanning can't tell you either.

**Don't invert which entry mode (warp vs. impulse) heals a barrier vs. permanently seals it.** This came up as a way to discourage "warp-fishing" - touring every barrier at warp specifically hunting for a cache, since a warp-entered barrier heals once warp disengages (see `warpEnteredBarrier` below) while an impulse-entered one stays sealed for good. The idea was floated and deliberately rejected: warp and subspace anomalies are both subspace phenomena, so warp passing through one is the *non*-disruptive case (fitting that it heals), while impulse - ordinary-space travel forcing its way through - is the actual intruder (fitting that it's the one that does lasting damage). The current polarity already matches that in-universe logic; flipping it would only be undoing it for a balance reason that doesn't hold up anyway, since `BARRIER_POWERUP_CHANCE` already makes a cache rare enough (~1% of sectors) that warp-fishing costs real mission time for a low hit rate. If warp-fishing ever does need discouraging for real, don't reach for this inversion - look at `BARRIER_POWERUP_CHANCE` or the warp energy-cost curve instead.

### Local leaderboard: localStorage, no backend

`game/leaderboard.ts` persists a plain `{ name, score }[]` to `localStorage` under a single key - no server, no accounts, since the whole game already runs client-only. `loadLeaderboard()` never throws: a missing key, corrupted JSON, a non-array value, or storage being unavailable entirely (private browsing, disabled outright) all just read back as an empty leaderboard rather than breaking the screen around it - and `saveLeaderboard` swallows write failures (quota exceeded, blocked) the same way, silently, since a lost high score isn't worth surfacing an error over. `addLeaderboardEntry` re-sorts by score descending and trims to `LEADERBOARD_MAX_ENTRIES` (`balance.ts`) on every write, so the stored list is always already in display order - callers never sort it themselves.

`game/Leaderboard.tsx` is one component shared between `StartScreen.tsx` (plain, read-only) and `EndScreen.tsx` (with a `pendingScore` prop), rather than two - the only real difference is whether there's a just-earned score to name and save. A loss has no score (see `missionScore` below), so `EndScreen` only ever passes `pendingScore` on a victory. While a pending score hasn't been saved yet, the component computes where it *would* rank among the current entries and splices in an inline name-input row at exactly that position - matching `addLeaderboardEntry`'s own tie-break (`>=`, not `>`, so an exact tie previews in the same slot a save would actually land it: after the existing entry, per `Array.prototype.sort`'s stability). If that position would fall outside `LEADERBOARD_MAX_ENTRIES`, no input row is shown at all - just a plain "didn't make it" note - since saving would only save-and-immediately-trim it away.

Its box and grid deliberately mirror `StartScreen.tsx`'s Controls reference panel (`.leaderboard`/`.leaderboard__list` copy `.start-screen__instructions`/`.start-screen__controls`'s width, 3-column `grid-template-columns`, gap, and the same `max-width: 480px` breakpoint dropping to 2 columns) so the two read as matching panels rather than one looking bolted on. Rank order still reads top-to-bottom at a glance because a row-major grid (the CSS default `grid-auto-flow`) fills left-to-right one row before wrapping - #1-3 land in row 1, #4-6 in row 2, and so on - not down each column first. Within a cell, `.leaderboard__row` is a horizontal flex row (rank, name, score inline, name truncating via `flex: 1; min-width: 0`) - the same horizontal-cell shape `.start-screen__control-row` uses, right down to the score sitting flush at the cell's right edge the same way `.start-screen__action` does. `.leaderboard__rank` carries a small `margin-right` on top of the row's own `gap`, specifically so rank and name read as more clearly separated than name and the (already far-right) score need to be. The pending cell's name input and Save button follow the same horizontal flow (the input is `flex: 1` too, so it's the one thing that actually shrinks if the row gets tight).

### Kill phase: bitECS

`kill/world.ts` defines the ECS world as plain typed arrays keyed by entity id (no schema classes - see bitECS 0.4 idioms). `KillPhase.tsx` owns the tick loop (`requestAnimationFrame`), running systems in a fixed order every frame: `hostileAiSystem → homingSystem → physicsSystem → boundarySystem → hazardSystem → collisionSystem → ageoutSystem`, then `pruneSystem` (removes anything marked `Dead` this tick) and `renderSystem`. Shield energy absorbs damage before hull health does (`collisionSystem`); `markDead` (in `world.ts`) is the single idempotent way to tag an entity dead - always use it rather than mutating the `Dead` component directly, so a later system's check for "already dead" stays correct.

Engineering's shield/phaser sliders are live-synced into the running world via a separate, lightweight `useEffect` (not the world-building one) precisely so adjusting them mid-fight doesn't trigger a world rebuild.

### UI structure

`HuntPhase.tsx` lays out three columns: a Controls panel (every player action - scan/warp buttons plus the energy shortcuts, also bound to keyboard shortcuts L/S/W/I/H/P), a main station (Sciences or Tactical), and a sidebar (Status or Damage-control, then Engineering, then Comms). The Sciences/Tactical and Status/Damage-control pairs each share one panel slot with a header that doubles as the tab toggle (see `Panel.tsx`'s `toggle` prop). Sciences/Tactical specifically uses `display: contents | none` on a wrapper div rather than a conditional render, because unmounting `KillPhase` would tear down its live bitECS world and rAF loop mid-fight - `paused` (checked inside the tick loop) is how it actually pauses, not unmounting.

`App.tsx` starts a new mission by bumping a `gameKey` counter passed as `<GameShell key={gameKey}>` - a full remount, rather than a hand-rolled reset path through every piece of state.

`game/StartScreen.tsx` (the difficulty picker shown before a mission starts) lays out as a true 3-column CSS Grid page (`.start-screen`, `display: grid`, `grid-template-columns: minmax(220px, 280px) minmax(380px, 460px) minmax(220px, 280px)`): Leaderboard on the left, title/description/hint/difficulty cards centered in the middle, Controls reference on the right, with generous `column-gap` and page padding so the three read as separate panels rather than one crowded block. The title sits in its own grid row above the three columns but placed in column 2 only (`grid-row: 1; grid-column: 2`), so it reads centered over the middle column rather than spanning the full page width; `align-self: end` pins it to the bottom of that row's track, since the row's height otherwise stretches to fill the page's leftover vertical space (CSS Grid's default stretch behavior) and `align-items: start` alone would leave it floating at the top with dead space below. The difficulty cards are a single row (`.start-screen__options`, `flex` with no wrap, each card `flex: 1 1 0`) rather than stacked, so they stay compact under the narrower center column. The Leaderboard and Controls boxes' headers (`.leaderboard h2`, `.start-screen__instructions h2`) deliberately mimic `Panel.tsx`'s in-game `.panel__title` styling (mono font, uppercase, letter-spacing, a colored `border-left` accent bar) - Leaderboard reuses the Status panel's cyan accent, Controls reuses the real in-game Controls panel's `#9aa5b8` - so they read as the same kind of panel as the bridge-station HUD the player is about to see; getting the accent bar to reach the box's full width required splitting each box into a header plus an inner `__body`/`-body` wrapper that holds the actual content padding. Leaderboard names are centered (`.leaderboard__name { text-align: center }`) specifically in this StartScreen context; `.start-screen__column--controls .start-screen__controls` and `.start-screen__column--leaderboard .leaderboard__list` are unconditionally forced to a single column (not gated by any media query - it's based purely on being nested under the StartScreen layout), which only affects these two components' StartScreen instances and leaves `EndScreen.tsx`'s separate, un-nested `<Leaderboard>` usage on its original 3-column/2-column-at-480px grid. Below `max-width: 1024px` (the 3-column grid's combined minimum width, floors plus gaps plus page padding, is too wide to shrink further), a `@media` block falls `.start-screen` back to a single flex column, using `order` to restore sensible reading order (title, then description/difficulty, then Leaderboard, then Controls) independent of the DOM order the desktop grid placement requires.

`game/EndScreen.tsx` shows a mission score, but only on a victory - a loss doesn't have a "how well did you do it" answer to give. `hunt/mission.ts`'s `missionScore` averages three equally-weighted factors (hostiles destroyed vs. quota, stardate spent vs. budget, energy/torpedoes remaining vs. starting amounts), scales the result so a no-time, full-resources win at exactly quota reads as `MISSION_SCORE_MAX` (1000, `balance.ts`), then multiplies the whole thing by the active difficulty's own `scoreMultiplier` (`DIFFICULTY_PRESETS` - 0.75 Easy, 1 Normal, 1.5 Hard) so the same relative performance scores more on a harder mission. `MISSION_SCORE_MAX` is a **target, not a cap** - the hostile factor is deliberately left uncapped, so destroying more than the quota requires pushes the score past it rather than topping out there (killing extra costs real time/resources anyway, so it isn't a free way to inflate the number). Don't clamp the final result to `MISSION_SCORE_MAX` if refactoring this - both the hostile-factor overkill and the difficulty multiplier are meant to push a score past it.

Both `StartScreen.tsx` and `EndScreen.tsx` end with a `Leaderboard` (see the "Local leaderboard" Architecture section above) - after the difficulty cards on the start screen, as the last block after the "New game" button on the end screen. Scores are already normalized *across* difficulties by `scoreMultiplier` above, which is exactly why the leaderboard doesn't segment by difficulty - a Hard win and an Easy win land on the same list on purpose.

**`App.css`'s cascade has caused two real bugs, both worth checking for before adding a new override.** CSS resolves same-specificity rules by source order, but a *more specific* selector wins regardless of order - two different mistakes, easy to conflate: (1) a media-query override placed *before* the base rule it was meant to beat loses to it every time on a matching viewport (this crushed `.hunt-sidebar` on narrow screens until the offending `@media` block was moved to the end of the file, after every rule it touches - see the comment there); (2) `.start-screen > p`'s own `color` rule (specificity 0,1,1 - a class plus a child combinator) silently overrode a same-named-but-plainer `.start-screen__hint { color: ... }` rule (0,1,0) even though the hint rule came later in the file - fixed by giving it the same `.start-screen > p.<class>` shape `.start-screen__subtitle` already used. When a new rule under `.start-screen` or `.hunt-phase` doesn't seem to apply, check both source order *and* selector specificity, not just one.

**A third `.hunt-sidebar` bug, unrelated to the cascade one above: `overflow-y: hidden` was masking a real crush, not preventing one.** `.hunt-sidebar`'s three panels (Status, Engineering, Comms) have no `flex-shrink: 0`, so on a landscape phone wide enough to skip the `max-width: 860px` narrow-screen breakpoint (an iPhone SE/14 in landscape, 667-844px wide, still hits it and is fine; a Pixel 7 or iPhone 14 Pro Max, at 915-932px, doesn't) there isn't enough height for all three stacked, and flexbox silently compresses them to fit - `.panel`'s own `overflow: hidden` then clips whatever no longer fits (Engineering's sliders, half of Status's stat grid, Comms crushed to ~0px). The fix: `.hunt-sidebar`'s `overflow-y` is `auto`, not `hidden`, and `.panel--status`/`.panel--engineering` get `flex-shrink: 0` - the auto-scroll alone did nothing while they could still shrink to fit, so both parts matter. `.panel--comms` keeps a `min-height: 110px` floor rather than collapsing to 0. If a sidebar panel's content looks silently truncated with no scrollbar, check `flex-shrink` on the panel before assuming it's the cascade bug above.

### Testing shape

The pure logic layer (galaxy generation, mission rules, subsystem math, ECS systems, `useGalaxy.ts`'s state transitions) has thorough Vitest coverage, almost all of it exercised via injected `rng`/`Math.random` mocks rather than relying on real randomness. There are no component-level tests (no interaction/rendering tests for the panels, `GameShell`, or `KillPhase`'s canvas rendering) - UI changes have historically been verified with live manual/Playwright passes during development, not automated regression tests.

## How the project got here

Started (2026-09-06) as a Vite+React+TS scaffold with `UndoGraph` and the anomaly primitives built first, before there was a game on top of them - the hunt-phase galaxy map, bitECS kill phase, and phase-transition layer (`GameShell`) followed the same day. Fog-of-war sensing and the energy economy came next, then the hunt-phase UI went through its first real restructure (Status/Comms/Engineering/Sciences panels) and shields/phasers became real, refundable combat resources rather than free stats.

Mid-September brought a wave of world-shape changes: rings switched from equal-area to equal-width, the galaxy grew to 6 rings, and per-ring angular resolution was introduced (coarse core, finer outer rings) - all in service of making the map read better at a glance. Anomalies were reworked repeatedly in this window: a "well" became a *barrier* (blocks entry, not exit), then anomalies overall were rebuilt around entry-triggered effects (barrier/gate/conduit), with several passes just on how each type reads on the map (marker glyphs added, then partly removed again once they cluttered more than they clarified). Starbases (auto-dock, restores shields/phasers/reserves) arrived in the same period.

Late September was the combat-depth push: torpedoes as a scarce secondary weapon, multi-hostile packs, star hazards, and the timer+quota win condition followed by stranding as a defeat condition (destroyed - real hull-to-zero defeat - didn't land until much later, see below). This is also when Tactical merged into the hunt-phase HUD as a Sciences-toggle panel instead of a separate full-screen mode, which is what makes `display: contents | none` (not unmounting) load-bearing for `KillPhase` today - and when a real bug (hostiles teleporting when Engineering sliders moved mid-fight) forced the stable-callback-identity pattern that `useGalaxy.ts`'s stale-closures note above documents.

Late September also did the two consolidation passes this codebase leans on: every tunable constant moved into `src/balance.ts` (previously scattered across modules), and a maintainability cleanup pass removed dead code and duplicated helpers. CLAUDE.md itself, the test suite for `useGalaxy`'s core transitions, and the MIT license all landed around the same time - this was the point the project shifted from "get it working" to "keep it working."

The most recent arc (2026-09-25 on) was about getting the game in front of a real player on a real device: a headless balance simulator (reusing the actual hunt/kill logic with a scripted bot, including a flee threshold so "stranded" - not "destroyed" - was the dominant failure mode) was used to derive Easy/Normal/Hard presets; a tablet/phone pass added on-screen touch controls, PWA icons, and a name unification (the game had been developing under "Subspace Wumpus" internally, "Nextrek" became the primary name everywhere - title, manifest, README, CLAUDE.md); and a live mobile-Safari test surfaced a real CSS cascade-order bug that was crushing the sidebar on narrow screens. That same real-device push is what exposed that "ship destroyed" was copy without a mechanism - `DefeatReason` only had `timeout`/`stranded` - which is why it was added for real as the third defeat condition (2026-09-26), as a sticky `shipDestroyed` flag rather than a derived threshold, checked first in status derivation.

A same-day follow-up pass (2026-09-26) tightened up combat feel and the energy economy's edges. The player ship used to spawn dead-center and motionless at the start of every kill-phase encounter even though hostiles have always drifted from spawn; `spawnPlayer` now takes a heading/speed the same way `spawnHostile` already did, with `pickPlayerSpawnHeading` (`kill/spawn.ts`) keeping that heading clear of a star hazard's direction when one's present. Separately, H/P keyboard shortcuts were added so a player can add shield/phaser energy mid-fight without reaching for the mouse (`useGalaxy.ts`'s `adjustEnergy`) - deliberately increment-only, no decrement key, because a decrement *was* available already via the Engineering slider (`allocateEnergy`) and turned out to be exploitable: dragging a slider down right before a fight resolved reclaimed that energy at full value instead of the `REFUND_EFFICIENCY` (50%) rate `resolveEncounter`'s own end-of-fight refund charges on unspent energy. That loophole got closed the same day by giving `allocateEnergy` an `inCombat` flag - a decrease while an encounter is active is now credited at the same lossy rate a real stand-down would be, so timing a slider drag against the end of a fight no longer avoids the cost. The same day also added a mission score to the victory end screen (`hunt/mission.ts`'s `missionScore`) - equal parts hostiles destroyed, time spent, and resources left, so "efficient" and "thorough" are both rewarded rather than the mission being pass/fail with nothing to compare between wins. A live check on a landscape phone wide enough to stay in the hunt-phase's 3-column row layout (a Pixel 7 or iPhone 14 Pro Max, unlike the narrower iPhone SE/14, which already hit the portrait breakpoint) turned up a third, unrelated `.hunt-sidebar` bug: its panels had no `flex-shrink: 0`, so flexbox silently crushed Status/Engineering/Comms to fit whatever short height was left, and `overflow-y: hidden` clipped the result instead of a scrollbar ever appearing. Fixed by switching that to `overflow-y: auto` and pinning Status/Engineering's height with `flex-shrink: 0`. The mission score itself picked up a difficulty multiplier the same day (`DIFFICULTY_PRESETS`' `scoreMultiplier` - 0.75/1/1.5 for Easy/Normal/Hard), applied over the whole three-factor average, so the same relative performance is worth more the harder the mission.

On 2026-09-28, barriers - previously pure downside, a one-way trip with nothing to show for it - got a chance to also hold a one-time energy or torpedo cache (`BARRIER_POWERUP_CHANCE`/`BARRIER_POWERUP_ENERGY_CHANCE` in `balance.ts`), revealed only by physically entering the sector, never by scanning. Collection is tracked in a new `HuntState.collectedPowerUps` set rather than on the graph node itself, specifically to avoid colliding with `UndoGraph`'s shared undo stack the way a barrier `setNode` write could (see the Architecture section above) - a risk this feature's design surfaced but that pre-existed it elsewhere in the code (`GameShell.tsx`'s combat-result path). A follow-up start-screen hint was added to the `HINTS` pool (`StartScreen.tsx`) nodding at the mechanic without spoiling it. The same day, a proposal to discourage "warp-fishing" (touring barriers at warp specifically hunting for caches) by inverting which entry mode heals vs. permanently seals a barrier was considered and dropped - see the Architecture section's note on it for why the current polarity is the one that actually matches the fiction.

A same-day follow-up turned the cache from one-shot into rechargeable: `collectedPowerUps` became a `Map<NodeId, number>` of last-drawn stardate, gated behind a new `BARRIER_POWERUP_COOLDOWN_STARDATES`, with `GalaxyMap.tsx`'s marker hidden while on cooldown the same way it's hidden before the first visit. This is what finally gave the warp/impulse entry-mode split a real stake beyond navigation - a repeatable cache is only worth anything if the barrier heals, so the choice of how you enter now actually matters for the reward, not just for whether the sector stays useful as a route afterward. Verifying this live surfaced a real, separate, pre-existing bug: disengaging warp after a warp-healed barrier entry didn't actually restore true impulse edges, because `disengageWarp`'s single `undo()` call only popped the barrier's own edge-removal, not the warp engagement underneath it. Fixed the same day - `engageWarp` now hands back a checkpoint (the graph's `undoDepth` from just before it pushed) and `disengageWarp` unwinds back to it via a new `UndoGraph.undoTo`, rather than assuming warp is always exactly one push deep - see the Architecture section's note on it.

On 2026-09-30, a local leaderboard arrived: `game/leaderboard.ts` persists `{ name, score }` entries to `localStorage`, no backend, and a single `Leaderboard` component (`game/Leaderboard.tsx`) renders on both `StartScreen.tsx` (read-only, after the difficulty cards) and `EndScreen.tsx` (with an inline name-entry row for a just-earned score, spliced into its actual rank, as the last block after "New game"). Scores from every difficulty share one list rather than being segmented, since `missionScore`'s own `scoreMultiplier` already normalizes across difficulties - that normalization is exactly what makes a shared leaderboard make sense at all. A same-day follow-up reworked its layout to mirror the Controls reference panel it sits near - full-width box, 3-column grid, same 480px breakpoint dropping to 2 columns - rather than the narrower single-column list it first shipped with.

On 2026-10-01, the start screen's single centered column (description/hint/difficulty cards, Controls reference, and Leaderboard all stacked one under another) was replaced with a true 3-column page layout - Leaderboard, title/description/difficulty, Controls - after the stacked version read as too crowded and the Leaderboard/Controls grids as a visually bolted-on afterthought. The redesign went through several iterative, screenshot-previewed rounds before being built for real: an initial pick among three generated layout variants, then aligning the Leaderboard/Controls boxes' tops to the description text (not the title) via a 2-row grid trick with explicit row/column placement, then a single-row difficulty-card layout, then moving the title to the bottom of its row via `align-self: end` (needed because CSS Grid's default stretch behavior left row 1 taller than the title needed, with `align-items: start` otherwise pinning it to the top of that excess space), then giving the Leaderboard and Controls headers an in-game look - mimicking `Panel.tsx`'s `.panel__title` treatment closely enough to reuse its exact accent colors (Status's cyan for Leaderboard, the real Controls panel's `#9aa5b8` for Controls), which required splitting each box into a header plus a padded inner body wrapper so the accent bar could reach full width - and finally centering leaderboard names within the narrower sidebar column. A title/subtitle overlap bug turned up mid-sequence (a stale `margin-top: -12px` on the subtitle, left over from the old single-flex-column layout's sibling `gap`, pulled it up into the title once the title moved into its own isolated row) and was fixed by removing it in favor of the title block's own small `gap`. Final verification before committing surfaced a real regression, caught proactively rather than user-reported: the 3-column grid's combined minimum width (column `minmax` floors plus gaps plus page padding, roughly 1028px) broke completely below ~1024px, pushing the side columns off-screen on phone and tablet. Fixed with a `max-width: 1024px` fallback that collapses `.start-screen` back to a single flex column, using `order` to restore sensible reading order independent of the DOM order the desktop grid's row/column placement requires.
